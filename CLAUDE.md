# Wishlist — pet project для друзей

Страница вишлиста ко дню рождения (и для других людей). Бесплатный стек, без своего сервера.
Владелец управляет проектом в основном с телефона через Claude Code Cloud, поэтому:
- держи README и этот файл актуальными;
- каждая задача заканчивается рабочим деплоем на GitHub Pages.

## Стек

- React + Vite + TypeScript, SPA с hash-роутингом (`#/list/:id`) — GitHub Pages не умеет SPA-fallback.
- Firebase: Firestore (данные + realtime через `onSnapshot`), Auth (Google для авторов, Anonymous для гостей).
- Хостинг: GitHub Pages, деплой GitHub Actions из `main` (`.github/workflows/deploy.yml`, `base` в Vite = `/wishlist/`).
- Конфиг Firebase лежит в коде (`src/firebase.ts`) — это публичные ключи, защита только через `firestore.rules`.
- Тариф Firebase Spark (бесплатный). Ничего, что требует Blaze/Cloud Functions.

## Сценарий

1. **Автор** входит через Google, создаёт вишлист (название, дата события, необязательные «Пожелания»), добавляет пункты.
   «Пожелания» — свободный текст: что автору в целом нравится и чего не дарить. Гости видят его над списком и в «Я дарю другое». Можно задать при создании и изменить потом.
2. Автор делится ссылкой `https://madmed677.github.io/wishlist/#/list/<id>`.
3. **Гость** открывает ссылку, вводит только имя (сохраняется в localStorage), вход анонимный и незаметный.
4. Гость жмёт «Буду дарить это» → пункт помечается «Забронировано».
   - Другие гости видят, **кто** забронировал.
   - Автор видит только «Занято», без имени.
   - Снять бронь может только тот, кто её поставил.
5. **«Подарим вместе»**: вместо брони одному гость может открыть сбор на подарок. Другие гости видят «Скидываются Аня и Боря», комментарий организатора и примерную долю (цена ÷ участников) и могут присоединиться. Организатор — первый участник; если он выходит, организатором становится следующий; последний вышедший освобождает подарок. Автор видит просто «Занято». Кнопку «Подарим вместе» показываем у всех свободных подарков, «сбор закрыт» не делаем.
6. Гость может добавить **свой подарок** («Я дарю другое»): автор его не видит вообще, остальные гости видят, чтобы не купить то же самое.
7. Всё в realtime: брони и новые пункты появляются у всех открытых вкладок сразу.

## Пункт вишлиста

Название (обязательно), описание/комментарий, ссылка на товар (опционально), картинка (URL, опционально), примерная цена, приоритет (очень хочу / хочу / было бы неплохо).

## Модель данных (Firestore)

```
wishlists/{listId}                     { ownerUid, ownerName, title, eventDate, wishes, createdAt }   ← wishes: «Пожелания», ≤ 1000 символов
  items/{itemId}                       { title, description, url, imageUrl, price, priority, createdAt }
  reservations/{itemId}                { uid, createdAt, group? }    ← видят все, включая автора («Занято»)
  reservationDetails/{itemId}          { uid, guestName }            ← автор НЕ видит
                                       общий подарок: { uid, guestName, group: true,
                                                        members: { <uid>: { name, at } }, note, noteBy }
  guestGifts/{giftId}                  { uid, guestName, title, description, url, price, createdAt }  ← автор НЕ видит
```

- `reservations` и `reservationDetails` создаются/удаляются одним batch-ом.
- Документ брони имеет ID пункта: правило разрешает только `create` (не `update`), поэтому двойная бронь невозможна — второй получит ошибку.
- Удаление автором пункта удаляет и бронь (batch на клиенте; правила разрешают владельцу delete брони, но не read деталей).
- Сбор: вступить/выйти — транзакция над `reservationDetails.members` (каждый меняет только свой ключ); последний участник удаляет и бронь, и детали. Комментарий может менять участник.

## Правила безопасности (`firestore.rules`) — главное

- `wishlists`, `items`: читают все авторизованные (в т.ч. анонимные), пишет только `ownerUid`.
- `reservations`: читают все; `create` — если `request.resource.data.uid == request.auth.uid` и пользователь не владелец; `delete` — сам бронировавший или владелец.
- `reservationDetails`, `guestGifts`: read — только если `request.auth.uid != ownerUid` списка; write — только свои документы (uid == auth.uid), не владелец.
- Известное ограничение: автор в инкогнито = гость. Это принимаем.
- **Правила публикуются отдельным workflow** `.github/workflows/firestore-rules.yml`: при изменении `firestore.rules` в `main` он гоняет тесты `tests/rules/*.test.mjs` на эмуляторе (`npm run test:rules`, нужна Java) и деплоит правила скриптом `scripts/deploy-rules.mjs` (Firebase Admin SDK; firebase-tools не подходит — у ключа adminsdk нет прав на serviceusage), если задан секрет `FIREBASE_SERVICE_ACCOUNT`. Меняешь правила — добавь/обнови тесты и проверь, что workflow зелёный и не написал предупреждение «секрет не задан»; если секрета нет — попроси владельца опубликовать правила вручную (README → «Правила доступа»).

## Настройка, которую делает человек (не код)

Проект Firebase: `wishlist-24cee` (конфиг уже в `src/firebase.ts`). Пошагово для телефона — в README.

1. Создать проект в https://console.firebase.google.com (Spark), добавить Web App, вставить конфиг в `src/firebase.ts`.
2. Включить Authentication → Google и Anonymous; добавить `madmed677.github.io` в Authorized domains.
3. Создать Firestore database, задеплоить `firestore.rules` (через консоль — скопировать файл, или `firebase deploy --only firestore:rules`).
4. GitHub Pages уже включён с источником «GitHub Actions».

## UI и дизайн

- Мобильный в первую очередь (друзья откроют ссылку с телефона), но есть и десктопная раскладка (≥ 900px).
- Тема: меню в шапке (`src/components/ThemeMenu.tsx`) — «Светлая» / «Тёмная» / «Авто (как в системе)»; по умолчанию «Авто». Выбор хранится в localStorage (`wishlist.theme`), «Авто» = нет атрибута `data-theme` на `<html>`.
- Язык интерфейса — русский.
- Дизайн-система «Вишлист»: https://claude.ai/artifact/QfvPkkecFeLMovM4ntmjA5 ; экраны и переходы (страницы «Телефон» и «Компьютер»): https://claude.ai/artifact/LNycnQHYLxqqZgGDrYCQDW
- Цены в примерах и плейсхолдерах — в тенге (₸).
- Токены: `src/styles/tokens.css` (значения из `design/tokens.json`). В `src/styles/app.css` и компонентах — только `var(--токен)`, никаких литеральных цветов.
- Кнопки и поля — компоненты дизайн-системы «Button» и «Input»: `src/styles/components.css` = копия `components/bundle.css` из дизайн-системы (меняешь — меняй в обоих местах). Классы: `btn` + `btn-primary` / `btn-danger` / `btn-ghost`, размеры `btn-sm` / `btn-lg` / `btn-icon`; поля — `input` (+ `aria-invalid` и `<span class="field-error">` для ошибки). У всех есть hover / active / focus-visible / disabled; при отправке формы — `disabled` + `aria-busy` (спиннер).
- Один шрифт — Manrope (разные начертания 400–800). Другие шрифты не добавлять.
- Основной цвет — синий `--primary`. «Занято другим» — оранжевые `--reserved-*`, «моя бронь» — зелёные `--mine-*`.
- Статус брони у любой карточки (желание, «Я дарю другое», превью) — только полоса сверху + рамка того же цвета (`CardMark` в `src/components/ItemCard.tsx`). Отдельных плашек статуса внутри карточки не делать.
- Сбор «Подарим вместе» — фиолетовые `--group-*` (`src/components/Group.tsx`).
- Иконки — линейные SVG из `src/components/icons.tsx`, без эмодзи.
- Имена не склоняем (Айгерим, Асель не склоняются): «Пожелания · Артём», «Артём просит учесть», «Артём · 14 декабря».
- «Пожелания» — голубой блок `--primary-soft` (`src/components/Wishes.tsx`); у автора пусто → пунктирная подсказка «Написать пожелания».
- Телефон: формы в шторке снизу, FAB «＋ Желание». Десктоп: боковая колонка + сетка карточек, формы — модальное окно по центру.

## Структура кода

- `src/firebase.ts` — конфиг, вход (Google с привязкой к анониму, анонимный), тексты ошибок, режим эмуляторов.
- `src/api.ts` — все запросы к Firestore и realtime-хуки (`onSnapshot`).
- `src/pages/` — `Home` (вход / мои вишлисты), `ListPage` → `OwnerView` или `GuestView`.
- `src/components/` — карточка пункта, формы, шторка/окно, иконки.
- Локально без настоящего Firebase: `npm run emulators` + `npm run dev:emulators`.
